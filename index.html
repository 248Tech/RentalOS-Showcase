What it does

Built around the real workflow of a rental company, from first inquiry to pull sheet. The demo lets you try each of these.

▦

Inventory & availability

Searchable catalog with categories, stock, set-asides and per-day availability. Overbooked items surface as conflicts before you promise them.

▤

Quotes & pricing

Line items, discounts, tax, custom items and contract text — with signed-versus-unsigned change tracking that forces re-approval.

✍

Client portal & signing

Shareable public quote page with click-to-sign approval. Each signature records the typed name, time, IP, user agent and a hash of the quote as signed.

☑

Pull sheets

Warehouse picking lists grouped by category, with aggregate pulls and QR/serial tracking for fulfillment.

🌐

Public SEO catalog

Canonical URLs, JSON-LD product markup, robots and sitemap generation so your inventory ranks.

✦

CINDY copilot

Optional, permission-aware assistant. It proposes quote and inventory changes that apply only after a user confirms, with undo. Works with OpenAI, Anthropic, Gemini or a local Ollama model.

Engineering highlights

Choices that go beyond the feature list.

Safe schema evolution

Startup migrations keep a live database upgradeable, with backup and a DB guardian service plus worker heartbeats and incident reflection.

Permissions by module

Role-aware navigation and per-module read/write permissions, including a dedicated check for AI copilot access.

Domain correctness

Shared totals logic, oversold detection across overlapping events, signed-quote change control and a guarded Rust parity path for the availability engine.

Documented & audited

Architecture and API docs, a security audit, release notes per version, and 85 test files covering server security, availability parity and client quote logic. CI for the suites is next.

Case study

Why RentalOS exists, how it is built, and what is not finished yet.

The problem

Event rental companies quote the same tents, tables and chairs for many overlapping events. Promise the same stock twice and someone finds out on the loading dock. RentalOS was built by Joe Wayne, who spent seven years in event rental operations, five of them in management, to make availability, quoting, signing and warehouse pulls one connected workflow.

Status

Pre-release testing. Single developer, AI-assisted. 13 tagged versions (v0.0.1 to v0.0.13). Single-tenant: one company per installation.

Design decision: confirmed vs potential stock

Only confirmed quotes reserve inventory. Drafts and sent quotes count as potential, so a salesperson sees a likely conflict without blocking stock for an event that may never book. After a client signs, only quantity added later counts as potential. The tradeoff is two numbers to explain instead of one.

Hard problem: proving what was agreed

Click-to-sign stores the signer's name, time, IP and user agent, the signed total, the signed line items and a hash of the quote snapshot. Later edits are tracked against that snapshot and require re-approval. It is click-wrap acceptance, not a drawn signature.

Optional AI, with a human in the loop

The assistant can propose changes to quotes and items. Nothing applies until a user confirms; permissions are re-checked at confirmation and changes can be undone. AI is off unless a provider is configured.

Experimental Rust engine

A Rust (Axum) implementation of the availability math can run in shadow mode next to the Node engine and log any disagreement. Parity tests compare the two. It is off by default and not part of the Docker image yet.

Testing

89 server tests (copilot security, Rust parity, assistant behavior) and about 160 client tests for public quote, catalog and SEO logic. Tests run locally; CI is not set up yet.

Known limitations

Single-tenant. No continuous integration yet. Signing is click-wrap and has not had legal review.
